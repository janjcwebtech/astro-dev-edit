# Image storage and media roadmap — sf-sf

These are improvement opportunities from the 2026-09-06 exploration, separate from [reproduced bugs](bugs.md). sf-sf's image structure is intentional; moving everything into public or broadening writable roots would not preserve its behavior.

## The actual storage and rendering models

The restored project contains **241 image files under src/assets** and **29 under public** (PNG, JPEG, GIF, WebP, AVIF and SVG counted). The picker initially offered 241 importable assets, with 72 in the note field's current folder. Counts increased only while the disposable upload existed.

## Suggested roadmap work

1. **Show where a visible image comes from.** Identify its collection field, Astro import, MDX component prop, raw SVG or remote URL before offering actions. Surface the owning usage file rather than stopping at a package-owned Image component. A useful acceptance case is the same note cover appearing on both the listing and its detail page.
2. **Make upload destination explicit and selectable within valid roots.** Existing image() uploads preserve the current asset folder, which worked here. Empty fields fall back to `src/assets`; sf-sf needs deliberate choices such as `src/assets/works/appcast`, `notes`, or `studio`. Show the destination before upload and preserve the relative import path. No automatic collection-name-to-folder assumption: roles already reuse a studio asset.
3. **Support nested object and repeatable block media.** Service testimonials, work results and MDX media compositions need controls at the actual field/prop position. Preserve comments, ordering, imports, responsive image settings and unrelated properties. Existing read-only JSON is a safe fallback, not a corruption defect.
4. **Keep storage constraints visible in the picker.** Distinguish importable src assets from public web assets and remote media. Explain why a public GIF is unavailable to an image() field, and retain the tested GIF refusal. Do not optimize away animation or transparency merely to make every asset selectable.
5. **Manage uploads that were never selected.** Uploading writes immediately; Cancel then leaves the new asset on disk while preserving the original field value. This was reproduced with `src/assets/notes/sf-probe-upload.png`. Show that distinction and consider a session upload list with usage checks and explicit removal. Cancel should not delete a file another field may already reference.
6. **Improve browsing at this project's scale.** The existing folder scope and text filter work. A directory navigator and usage/reference lookup would make 241 source assets easier to manage, especially similarly named case-study images. The current 72-image notes scope loaded without broken thumbnails; performance at substantially larger scales was not measured.

Two adjacent authoring limitations deserve separate backlog entries: the file-loader `archive` holds **14 JSON records**, while Collections assumes `src/content/archive` and reports “directory missing / 0 entries”; and complex MDX remains source-only. Both reflect the documented collection/file-shape boundaries. No schema conversion, archive migration, asset relocation, or implementation change was made.
